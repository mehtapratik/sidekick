An **entity** is anything linkable in any module: a Taxila datum or narrative, a War Room plan, an Alter Ego chat session, a scheduled job. A **datum** is Taxila's compact entry, one fact per entry; a narrative can be built from datums, and datums can be split out of a narrative.

## The entity index

Synergy (`packages/platform/synergy`) keeps one thin row per entity, written when the entity is created and updated with it. The index answers every question that crosses modules (staleness, backlinks, search, delete blocks) without asking each module. Anything richer, like a card's excerpt or a live preview, comes from the renderer of the entity's **provider** (the package that registered its type) at render time.

**System fields** always exist and the user never fills them in or sees them as metadata:

| Field              | Meaning                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`               | Client-generated UUID                                                                                                                                   |
| `owner`            | The user who owns the entity                                                                                                                            |
| `provider`, `type` | The package that registered the type, and the entity type; the type's registration names the feature whose entitlement gates it                         |
| `status`           | `active` (default), `deprecated` or `superseded`; an entity is shown as deleted when it is soft-deleted                                                 |
| `version`          | Goes up only when the author flags a change that might invalidate references                                                                            |
| `revision`         | Goes up on every other save                                                                                                                             |
| `display_name`     | The title, or a short name the module derives from the content when there is no title                                                                   |
| timestamps         | `created_at`; `updated_at` (any write, metadata and tags included); `edited_at` (author content only, moves with the version or revision); `deleted_at` |

**User metadata** is all optional: title, tags, change notes, and anything a module adds. The user, or the bot or agent that produced the entity, picks what matters. Many datums are a sentence or two, so metadata must never be required.

## Versions and revisions

- The author decides when a change is a new **version**. An AI assistant may advise on its impact on dependents; the author has the final say.
- Every other save is a new **revision**: new content, grammar, formatting.
- Only author content counts: title, body and blurb. Metadata, tags and status never bump either counter. A content change also sets `edited_at`; `updated_at` moves on every write. Which one a "Last updated" label shows is a UI decision for later.
- A version bump may carry an optional one-line **change note**, stored in Synergy's version log.
- Versions are plain integers. Keeping full content snapshots per version, which diffs need, is each module's job.

## Lifecycle

- **Deprecated:** still readable, marked as out of date.
- **Superseded:** retired and replaced, through a `superseded-by` link from it to one or more replacements. Removing the last one makes it active again.
- **Deleted:** soft-deleted, shown as the status `deleted`. A restore brings back the status it had. The index row stays as a tombstone so a link can still name what it pointed at. An entity with incoming references can't be deleted (see [[04.prd.features.synergy.keeping-links-true|Keeping links true]]).
- Status changes never bump the version.

## Terms and the Lexicon

The **Lexicon** is the user's dictionary, and it lives in Taxila. Each entry is a Taxila entity of type `term`, not a row in a separate glossary table. Its title is the term ("War Room", or an acronym such as "TLDR"), its blurb is a one- or two-sentence definition or expansion ("too long; didn't read"), and it carries optional aliases and abbreviations ("WR"), which all resolve to the one term.

- Any word in any entity links to a term with a `defined-by` association. Rewording a definition never marks the documents that use it, and a term in use never blocks its own deletion, though a deprecated or superseded term still shows the red dot.
- The link renders as a minimal link: the word is the label. In the MVP, hovering shows the definition in the browser's own tooltip, and an acronym uses the native abbreviation element so assistive technology reads the expansion too. Clicking opens the term's entity in Taxila, which can link on (`explained-by`) to a fuller entry.
- One link serves both the quick reader and the curious one.

## Watch

Metadata on micronotes can outweigh the note. Observe real use and study how other tools handle properties on small notes before deciding whether metadata should scale with the size of the entry.
