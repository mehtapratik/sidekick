A reference records the target's version and revision when it is made. Every state below is computed when the link is read, from that snapshot and the target's index row. Nothing is written to referencers when a target changes.

## States

| State      | When                                                                 | What the reader sees                                                            |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Fresh      | Nothing moved since the link was made                                | The link                                                                        |
| Edited     | Revision moved, version didn't                                       | A standard-colour dot after the status                                          |
| Changed    | Version moved                                                        | A red dot after the status, and the change note where the display type has room |
| Deprecated | Target status is deprecated                                          | The status                                                                      |
| Superseded | The target has a `superseded-by` link to a replacement               | The status, and the successor where there is room                               |
| Deleted    | Target is a tombstone                                                | Name and status as plain text, no content, not clickable                        |
| Locked     | The feature gating the target's type isn't enabled for the reader    | Name, type and status as plain text, no content                                 |
| Redacted   | Reader may not see the target (after references between users exist) | Nothing about the target                                                        |

An entity has exactly one status. Edited and changed are marks, not statuses, so "deprecated and changed" shows `[deprecated]` followed by a red dot. The dots follow how code and text editors show a dirty file. Colour is never the only cue: the two dots also differ in shape (hollow for edited, filled for changed), and each has a text equivalent. Minimal links show none of the text; they get the red dot for changed, deprecated, superseded or deleted, and nothing for edited.

## Roll-up on the source

An entity's title shows a dot when any of its outgoing references needs attention: red for changed, deprecated, superseded or deleted, standard for edited, with the links as the reason. It covers links held only in a field too. It is computed on read, like every state here.

## Acting on a stale link

Only the source's author acts. Readers see the mark and the change note.

- **Still holds:** moves the snapshot to the current version and clears the mark.
- **Point to the new entry:** for a superseded target. With more than one replacement, the author picks one.
- **Unlink.** Any mentions of the link in the target then show "No longer linked" until their author dismisses or relinks them.

Post-MVP, readers can report a broken or obsolete source to its owner.

## Deleting a target

- An entity with any incoming reference can't be deleted. Associations never block. The owner deprecates or supersedes it instead, which keeps it readable for everyone who relied on it. Once no references remain, delete works.
- A referenced passage (a paragraph, sentence or word others link to) is protected the same way: removing it takes a new version or a supersede, never a plain save. See Relationships, Anchored links.
- Deleting a source soft-deletes its outgoing relationships, which can free its targets.
- Restore brings back what the delete removed and never touches the version.
- Permanent erasure (account deletion, privacy request) overrides the block. Incoming relationships are erased, and referencers show "a linked item was permanently removed".
- Revisit once real use shows whether blocking delete for the owner's own references is too strict.

## Server-side decisions

Locked, redacted and deleted are decided on the server before any renderer runs, with the same entitlement check `withApiGuard` uses. Synergy takes feature keys as data and never imports the feature registry or a feature. The browser never receives content it shouldn't, and API keys follow the same rule with scopes narrowing further.

## Notifications (post-MVP)

Notifications most likely live in Taxila and are configurable. The author learns how many referencers a change affects; referencers learn their source moved. A periodic digest is a reader like any other: one indexed query per user. Instant alerts fan out asynchronously from the outbox, never inside the save.
