A Rich Live Link is how a relationship appears inside any document, in any module, and in apps outside Sidekick. Nothing is ever copied; the link shows the target where it lives. It is the only UI Synergy ships to real users. Phase 3 also has a playground page behind the `sandbox` entitlement, for the owner to see relationships, tags and links on mock entities.

## Display types

A direct mention picks its display type, so a document can show several, and the source and the target can show the same link differently. Readers can't change it. An alias mention shows the author's words like a minimal link.

| Type                 | Shows                                                                                                                | When                          |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **Inline** (default) | `{title} ({type}) - [{status}]`, then a dot if the target moved                                                      | Unlabeled links               |
| **Card**             | Title, excerpt and module fields from the renderer, status, marks, change note                                       | Unlabeled links               |
| **Live preview**     | The whole target in place, current content, with the change note if it changed                                       | Unlabeled links               |
| **Minimal**          | The link's label, or the target's title when it has none, with a red superscript dot when the target needs attention | Labeled links, alias mentions |

- A minimal link carries a browser-default tooltip, `{type} - {status}`, so the label stays clean and the details are a hover away. A term link's tooltip shows the definition instead.
- Previews don't nest. Links inside a live preview render inline.
- A changed target's preview shows current content. "As linked" views and diffs are post-MVP.
- The MVP is plain text: no type icons, no status pills, no hover cards. Styling is added later without touching the contract.

## Who renders what

The component owns the frame: display type, status, marks, and the loading, error, empty, locked, redacted, deleted and "No longer linked" states. A mention in the target reads with the inverse type name. The component lives in Synergy and builds on `packages/ui` primitives. The content comes from the type's provider in two steps: a **resolver** fetches the render data (plain JSON, so it can be cached and sent to any consumer) and a **renderer** turns that data into React children, which the component puts inside its frame. Sidekick renders links on the server for a page's first paint and in the browser while you edit, for example when you insert a new link.

- Every module ships a renderer for each entity type that can appear as a link: datum, narrative, plan, chat session and so on.
- Inline and minimal need no renderer call. Everything they show is in the index.
- Card and live preview call the renderer.
- **Open to new types.** Any package adds a linkable type by registering the type, a resolver and a renderer; Synergy and the component never change. Tomorrow that could be a Twitter thread or a news article, linked and associated like any entry. Because the component doesn't know how to render any type, a renderer can also come from outside Sidekick (a Slack thread, say). Storing external links stays Taxila's job.

## Outside Sidekick

Rich Live Links are consumable by third parties. When Notion or Slack shows a Sidekick link, it can show the same card or live preview, with the same states and dots, through the same public API (One Interface). So the component assumes nothing about its host: no app-wide context, and a transport passed in (`resolveLinks(requests) => Promise<ResolvedLink[]>`), so each host decides how a request travels and with whose credentials. Its output can also be served as an embed, and a third party can render the same JSON its own way. The MVP builds the component this way; the integrations themselves (Slack unfurls, Notion embeds, oEmbed) are post-MVP candidates.

## Renderer contract

- **Fetching and drawing are separate.** `resolve` is async from day one and returns serialisable render data; `render(data)` is a pure function from that data to React. Only render data is cached; states (including those of links shown inside a live preview) are read fresh every time.
- **Server and client halves.** The resolver is registered in server code and the renderer in client code, so database code never reaches a browser bundle.
- **Batched:** links on one page are grouped by provider, and each provider gets one resolver call. A plan page with 20 datums, 8 tasks and 2 chat sessions makes 3 calls, not 30.
- **Never called** for deleted, locked or redacted targets, or for a type whose provider is no longer registered (shown like locked).

## Machines

Bots, jobs and agents get the same resolved link as structured data through the same API: relationship, target index fields, state and marks, and render data when asked for. They ignore the display type.

A throwaway prototype of the display types and states is published as a private page, linked from [[02-prd/03-features/01-synergy/tickets/08-rich-live-link-draft|ticket 08]].
