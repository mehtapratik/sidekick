**What gets built:** links that live in content. A note's body can mention a link (a mark carrying the relationship id), and the note's save tells Synergy every relationship id its content now mentions. Synergy compares that set with what it stored, keeps `mentioned` true or false on each link, creates the links the save declares, and tombstones a link once its source neither cites nor mentions it.

**Implements:** [[06-decisions/technical/mentions-and-link-lifetime|Mentions and link lifetime]], [[06-decisions/technical/anchors-in-content|Anchors in content]] ("one save call, reporting the current set"), the overview's Write path ("Save content" steps 5 and 6, "Link from content") and Content helpers ([[03-system-design/functional-design/04-synergy/00-overview|Synergy]]).

**Learning payoff:** sending the current set instead of the changes, and why that makes a write self-healing and safe to retry; computing a set difference in SQL; Tiptap's JSON document shape (nodes, marks, attributes) without an editor; one helper (`extractRefs`) shared by every provider; a rule enforced on the server that the client can't skip ("a save may only mention links with one end at this entity").

**Coach reads first:** the two decisions above, the overview's save steps, lesson 4's note save route, lesson 6's relationships code, [Tiptap's JSON format](https://tiptap.dev/docs/editor/core-concepts/schema).

## Steps

**Good to write yourself:** the set comparison (step 3), first as a sketch of which rows change, then as SQL.

1. **The mark.** Decide the minimal Tiptap JSON for a note body: paragraphs with text, and a link mark whose attributes carry the relationship id. Only what tests need; the real editor comes later.
2. **`extractRefs`, mentions part.** In `@sidekick/synergy/contracts`: walk the JSON and return the mentioned relationship ids (block and anchor ids join in lesson 10).
3. **`entity_mentions` and the comparison.** The table (entity, relationship id). On save, Synergy takes the reported set, refuses a mention whose relationship has neither end at this entity, inserts and deletes `entity_mentions` rows, sets `mentioned` on the affected links, and tombstones links with neither `cited` nor `mentioned`. All under the user lock, in the provider's transaction.
4. **Links from content.** The save may declare new links (id generated by the client, target, type, label). Synergy creates each with `mentioned = true` and `cited = false`, with the cycle check for references. Removing the text later removes the link.
5. **Wire the provider.** The note's save route calls `extractRefs` on the new body and sends the set and the declared links with the save.
6. **Prove it.** Integration tests through the note routes: a save that adds a mark and declares the link creates it, mentioned and uncited; a later save without the mark tombstones it; a link that is also cited survives losing its mention; a save that mentions someone else's link is refused; re-sending the same save twice changes nothing the second time; a link mentioned from both ends stays one relationship and creates no cycle; removing the source's last mention leaves the target's mentions showing the tombstone ("No longer linked"); the outbox shows created, cited and deleted events as expected.

**Exit check:** step 6 green in CI.

**Unit-test candidates:** `extractRefs` on hand-written Tiptap JSON.

**Out of scope:** anchors and block ids (lesson 10), the editor and its marks UI (Phase 4 or 5, decided at Checkpoint 3a).
